# MIDI8BIT · 网页版 8-bit MIDI 播放器

在浏览器里把 MIDI 用芯片音色（方波 / 脉冲 / 三角 / 噪声 + 鼓机）播放出来，
带示波器、音符卷帘和播放列表。**单文件、零依赖、纯离线**。

## 打开

直接打开 [index.html](index.html) 即可。
单文件、零依赖、不需要构建、不需要联网。

**iOS 上推荐用 HTML5Builder 作为运行基础**：把本文件夹放进 HTML5Builder 的站点目录，
由它打开 `index.html` —— 常驻使用、文件管理与离线运行都由它托管，比在别的 App 里
临时预览更稳。

不想拷贝源码的话，可以到 [Releases](../../releases) 下载单文件 **`midi8bit.html`**，
改名不影响使用，丢进任何 WebView 都能直接跑。

## 加载你自己的 MIDI
三种方式，任选：

1. **＋添加** 按钮 → 从「文件」App 里选 `.mid / .midi`（可多选）
2. **拖拽** 文件到窗口任意位置（桌面浏览器）
3. **内置清单**：把 MIDI 文件丢进本文件夹，然后编辑 `playlist.json`：
   ```json
   [
     { "file": "song1.mid", "name": "曲名一" },
     { "file": "sub/song2.mid" }
   ]
   ```
   刷新页面即自动出现在播放列表里（文件路径相对于本目录）。

## 后台播放 & 系统播放器联动

**架构：离线渲染 + `<audio>` 元素。**

早期版本用「实时 Web Audio 合成」，这在 iOS 上**根本走不通**。
WebKit 官方 bug
[263627](https://bugs.webkit.org/show_bug.cgi?id=263627)
《[iOS] AudioContext is not consistently resumed when page is brought to foreground》
与 [276687](https://bugs.webkit.org/show_bug.cgi?id=276687) 记载：

> 页面进后台后，AudioContext 报 `state='running'` 但 `currentTime` 不再前进，
> 或干脆不再出声；只有 HTML 媒体元素能在后台继续播放。

所以现在改成：

1. 选中曲目后用 `OfflineAudioContext` **离线渲染整首**（按内存预算分块：单块输出 Float32
   不超过 24MB，立体声 44.1k 下 63 秒一块、超 7 分钟转单声道后 134 秒一块，左右各留 4 秒
   余量防止延音被切断），得到 44.1kHz / 16bit WAV（超过 7 分钟的曲子自动降为单声道，省一半内存）；
2. 交给 `<audio>` 元素播放 —— **后台播放、锁屏控制、进度条、拖动全部原生支持**；
3. 示波器不再用 `AnalyserNode`，而是直接读渲染好的波形（还顺带做过零触发对齐），
   声道高亮则读一份预先算好的「活动网格」。

因此不再需要静音保活轨、预排程、墙钟对时这些补丁，代码整体反而简单了。

渲染耗时：57 秒 / 1909 音符约 1–2 秒，界面显示「渲染中 x%」。

### 位深量化为什么要先归一化

干声混音后的峰值只有约 **0.27**，而量化器的量程是 ±1 ——
直接量化的话 6bit 的 64 个台阶里只用到十几个，听感远低于标称位深（又闷又碎）。

所以导出时先做**响度归一**（ITU-R BS.1770-4 / EBU R128 积分响度，目标 `TARGET_LUFS = -16`，
400ms 窗 / 100ms 步进的**重叠块** + 双门限：先剔除低于 -70 LUFS 的块，再以通过者的整体响度
-10 LU 作相对门限；整首都不到绝对门限时**不做归一**，避免把底噪抬高 24dB），
再经**软拐点限幅**（`LIM_KNEE = 0.62 / LIM_CEIL = 0.92 / LIM_RATIO = 5`）把峰值收到 0.92，
然后才量化 —— 量化台阶全部落在有信号的区间里。
实测不同位深下前 20 万个采样里的不同幅值数：

| 位深 | 归一化前 | 归一化后 |
|---|---|---|
| 关 | 1788 | 6923 |
| 8bit | — | 1065 |
| 6bit | — | 255 |
| 4bit | 110 | 66 |

电平（rms 0.030 / 峰值 0.27）完全不变，只是量化细了 3.3 倍。

### 位深切换是"免费"的

位深量化（WaveShaper）是信号链的**最后一级**，所以干声只渲染一次，
不同位深在导出阶段套同一个传递函数就行 —— 切位深从"重渲染 1~2 秒"
变成"过一遍数据"：整首 508 万个采样点实测 **19 ms**（约 510 MB/s），
再加上缓存命中，基本是瞬时的。

### 预渲染与内存

- 选中一首后会**在后台顺序预渲染列表里的其它曲目**（先备下一首），
  连当前位深的成品一起生成。
- 切歌用**双缓冲**：两个 `<audio>` 元素轮换，空闲的那个提前把下一首加载解码好，
  歌一放完就直接换过去，不会因为 load / 解码停顿；切歌时的重活（画封面、重绘卷帘）
  也推到下一轮，不挡声音。
- 播放列表里名字前的**绿点**表示这首已经备好。写盘是异步的，
  所以绿点在"写盘确认"之前就会点亮（乐观），写失败时 `storeMaster` 会把它撤回来
  —— 相当于容忍最多 20 秒的窗口期，换取"不用等写盘完成就亮灯"。
- 所有缓存共用一个 **`CACHE_BYTES` = 1 GB 预算**（实测同源配额约 9.6GB，占 ~10%），按**字节**累减淘汰（最旧的先出，永远保住当前曲目）。
  - 淘汰只有 `evictCache()` 一个出口：先清"字节数未知"的历史条目（`b` 字段是后加的，
    老索引里没有；它们不计入总量，混进按字节的循环会让预算永远减不下去），
    再按预算从最旧的开始删，当前曲目全程豁免，且至少保留一条（否则会同一条"渲完就删"无限重渲）。
  早先是按条数（`CACHE_MAX = 32`），长曲子上最坏能到 GB 级，已改；
  超过预算的条目在**启动时**和**每次写盘时**由 `evictCache()` 统一淘汰。

### 自动下一首

一首放完自动切下一首并接着播（最后一首放完则停止）。
勾选「循环」则改为重播本首。

**诊断页**：<a href="audiotest.html">audiotest.html</a> 用来确认
「同源文件 / blob URL / data URL」三种音频来源哪些能加载。

> ⚠️ 这条链路依赖宿主 App 是否声明了后台音频能力（iOS 的 `UIBackgroundModes: audio`）。
> 如果切出去就断音，说明宿主没开这个权限。

## 音色映射（GM 全量）

**不是按 GM 的 16 个"族"一刀切**，而是 128 个音色逐个映射到
「波形 + 包络」两件事上：

- **波形**（决定音色）：12.5% / 25% / 50% 脉冲、三角、锯齿、正弦、噪声
- **包络**（决定怎么发音）：`perc` 敲击 / `pluck` 拨弦 / `bell` 铃类 /
  `wind` 管乐 / `lead` 主音 / `sus` 持续

  敲击类的包络是「起音 → 瞬态落到 strike → **一路衰减到音符结束时到达 sus** → 放开」，
  衰减终点跟着音符长度走，所以 MIDI 里写了多长就响多长（低音余音更足，
  `tailLevel()` 按音高加权）。

抽样对照：

| GM# | 音色 | 波形 | 包络 |
|---|---|---|---|
| 0 | Acoustic Grand Piano | 脉冲 25% | perc |
| 4 | Electric Piano 1 | 三角波 | perc |
| 8 | Celesta | 三角波 | bell |
| 16 | Drawbar Organ | 方波 50% | sus |
| 24 | Acoustic Guitar | 脉冲 25% | pluck |
| 32 | Acoustic Bass | 三角波 | pluck |
| 40 | Violin | 方波 50% | sus |
| 56 | Trumpet | 脉冲 25% | wind |
| 80 | Lead 1 (square) | 方波 50% | lead |
| 112 | Tinkle Bell | 正弦 | bell |

注意同一族内部是有区别的，比如 24-31 吉他里，
29/30 失真吉他是锯齿波、31 泛音是正弦；32-39 贝斯里，
32/33/34 是三角、35 是正弦、36/37 是脉冲 50%、38 是三角、39 是锯齿。
（34「拨片贝斯」用三角波、38「合成贝斯 1」也用三角波，与常识里的"拨片=脉冲"
不太一样 —— 这看着像表里的错位，但改它等于改音色、必须 `MIX_VER + 1`
让所有缓存失效，收益又不明确，故按实际行为如实记录，见 `DECISIONS.md` 补记。）

**打击乐**：覆盖 GM 打击乐 **35~81 全部 47 个音高**，
每个音高都有独立的合成方式（音高扫频的正弦 + 滤波噪声的组合），
包括邦戈、康加、定音鼓、阿哥哥、沙锤、木鱼、三角铁这些冷门音色。

改动波形或静音会标脏重新渲染干声；面板里显示的是「自动」实际解析出的波形。

## 渲染速度

渲染的耗时**几乎全在音频线程**（实测建节点只要 0.024 ms/音符，
20 秒音频的实际渲染要 831 ms），这部分绕不开。已做的优化：

- 音量直接折进包络的取值里，**省掉每个音符一个中间增益节点**（整首少几千个节点）
- 离线渲染不做活动追踪（本引擎**只有离线渲染这一种用法**：唯一的构造点传的就是
  `OfflineAudioContext`，所以节点回收那套代码已整体删除）
- **只在真的算久了才让出主线程**（每块都 `setTimeout(0)` 会被节流反拖慢）
- 分块渲染（立体声 44.1k 下 63 秒一块、超 7 分钟转单声道后 134 秒一块，按内存预算自适应），
  把"块尾余量"的额外开销压到最低

最有效的一招是**缓存**：同一首歌 + 同一套波形/静音设置只需要渲染一次，
干声存进 IndexedDB（位深不影响，量化在导出阶段做），
之后打开页面直接从缓存读 —— 实测 **4 ms vs 真渲染 4.3 秒**，约 1700 倍。
缓存按 **1 GB 字节预算**淘汰，超出时从最旧的开始删。

## 音质细节

- **脉冲波用精确傅里叶系数**：理想 0/1 方波在 `[0, duty)` 上展开，
  `a_n = sin(2πnd)/(πn)`、`b_n = (1-cos(2πnd))/(πn)`。
  实测高电平占比 12.2% / 24.7% / 49.4%（目标 12.5 / 25 / 50）。
  早期版本只写了 `b_n` 且漏了相位项，合成出来其实是**窄尖峰串**而不是脉冲。
- **波形等响度补偿** `WAVE_GAIN`：各波形 RMS 差很大（脉冲 12.5% 只有 0.34，
  方波 0.85），补偿 70% 让不同音色的音量接近，同时保留各自性格。

### 音色柔化与量化降噪

- **干声渲染**时主输出依次过：高通 35Hz → 低架 200Hz/-1.5dB → 高架 4kHz/+1.5dB
  → 两级低通（`TONE_LP = 10000 Hz`，24dB/oct），
  削掉方波最扎耳的高次谐波。想更亮/更闷改这一个数。
- **量化之后**再按位深补一道低通（`BITS_LP`：6bit→7kHz、4bit→5.5kHz），
  压掉台阶噪声的高频部分。（低位深才会加，8bit/关 不加 → 不会发闷）
- **电平门限**（`HARD_LEVEL = 0.05`）：量化台阶在小信号上会变成刺耳的"丝丝"声，
  所以低于该电平的部分逐渐不做量化 —— 安静段干净了，大信号仍保留颗粒感。
- **缓存淘汰**按缓存的**写入时间**最旧先出（当前曲目豁免），被踢的曲目绿灯熄灭（诚实反映不能秒播），
  但 `RENDERED` 不清 —— 预渲染链只补"从没渲过"的，杜绝淘汰→重渲的死循环。

## 解析器支持范围
SMF format 0 / 1 / 2（format 2 的多个独立序列会按时间轴合并播放，不当作多首歌）、running status、SysEx 跳过、
Tempo map（曲中变速）、CC7 音量 / CC10 声像 / CC11 表情 / CC64 延音踏板、Pitch Bend 解析。
（踏板与表情在音符起点取样，不做逐帧调制。）

**字节流的宽容度**：meta / SysEx / 系统消息**不会**清掉 running status（规范说会，但老音序器
确实在 meta 之后继续用裸数据字节发音，清零等于整轨丢音符）；系统公共消息（0xF1/0xF2/0xF3）
按各自的数据字节数跳过；`End of Track` 之后不再解析填充字节。

**解析但不参与播放**的字段：拍号、`division`（PPQ）、SMPTE 时基 ——
它们会被读出来放进 song 对象，但播放只按 Tempo map 换算时间。
轨道**内部**数据残缺（声明长度与实际事件不符）会明确报
"文件数据不完整，或不是标准 MIDI"，不再抛裸的 `Out of bounds access`。

## 已知限制
- 音频必须由用户点击后才出声（浏览器自动播放策略）。
- 页面切到后台时 `requestAnimationFrame` 暂停，示波器与卷帘会静止；声音不受影响
  （走的是 `<audio>` 元素，这是整个架构选离线渲染的原因）。
- SMF **format 2** 的多条独立序列会按时间轴合并播放（不当作多首歌），节奏与原曲不一致 ——
  这是有意为之的取舍，遇到这类文件请自行另存为 format 0/1。

## 改代码前请先跑测试

```sh
node test/parse_test.js      # 应输出 RESULT: PASS
node test/unit_test.js       # 应输出 RESULT: PASS（案例数会随测试增长，别写死数字）
node build.mjs --check       # 应输出 "index.html 与 src/ 一致" + "ARCHITECTURE.md 行数与 src/ 一致"
```

**为什么要先 build**：`index.html` 是 `src/` 的拼接产物，直接改 `index.html` 会在下次
build 时被覆盖。正确顺序是改 `src/` → `node build.mjs` → 跑测试。

**为什么需要测试**：脚本语法出错或漏一行，页面**不会崩**——顶多控制台报错、
某个按钮失灵，其余部分照常显示，只有真正导入并解析一个 MIDI 时问题才暴露。
（播放列表来自 `playlist.json` 或用户拖入，**不**来自 IndexedDB —— 缓存里只有音频。）
历史上 5 次"文本替换丢/错一行"里有 4 次属于这一类（都能编译通过、页面都能开）。

它从 `src/02-midi.js` 里把 `[PARSE-BEGIN]` … `[PARSE-END]` 之间的纯算法段抽出来
（产物 `index.html` 已剥离注释，标记只存在于源码），
在 Node 沙箱里跑三个真实 MIDI，断言音符数 / 事件数 / 时长（258 / 3122 / 1909）。
`index.html` 本身仍是**单文件零依赖**，`build.mjs` 与 `test/` 只是开发工具。
